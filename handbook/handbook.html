1. إيه هو burhan

الـ coding agents بتقول “done” من غير دليل. burhan هو spec-driven development لـ Claude Code وCodex. الـ story والـ plan هما الـ spec: إنت بتوافق عليهم قبل أي كود، وكل acceptance criterion مربوط بـ test، وكل خطوة build بتتراجع، وأي خطوة بتخرج عن الـ plan بتتسجّل. أوامر المهمة والـ hooks (scripts صغيرة بتبلّغ في لحظات محددة) بتحتفظ بالسجل.

خلّي أربع حاجات منفصلة. الاتفاق بيقول إيه المفروض يحصل. الـ hooks بتبلّغ. الـ ledger بيسجّل اللي اتشغّل. وإنت اللي بتملك الموافقات والـ commit وقرارات المخاطرة.

المصطلحات. الـ sub-unit هي خطوة build صغيرة متخططة. الـ gate نقطة الـ agent بيستنى عندها إنت أو إثبات (S story، P plan، T بناء test-first، R review، V verification، Q QC، K knowledge). الـ QC هو الفحص النهائي المستقل إن كل acceptance criterion اتسلّم. الـ baseline هو السجل اللي وافقت عليه (أو تنازلت عنه) لفهم الـ agent للمشروع. والـ knowledge review هو المكان اللي الـ agent بيقترح فيه دروس تستاهل تتحفظ وإنت بتحتفظ بيها أو بترفضها.

اللي burhan مابيدّعيهوش

مفيش hook بيمنع أي إجراء: الـ hooks بتبلّغ وبتفشل مفتوحة (fail open). أوامر المهمة بترفض خطوة غلط في الـ lifecycle، لكن الـ agent ممكن يتخطاها، والـ block اللي init بيكتبه في CLAUDE.md أو AGENTS.md تعليمات، مش قفل. burhan مايقدرش يثبت شغل محدش بلّغ عنه.

2. التسطيب وأول setup

المتطلبات: Node 22+؛ و Claude Code 2.1.139 أو أحدث و/أو Codex بعد ما توافق على الـ hooks بتاعته؛ والـ kit مسطّب في المشروع (npm i -D burhan-kit) أو على الـ PATH (npm i -g burhan-kit). هنا burhan معناها الـ kit command بتاع المشروع، اللي مكتوب في .burhan/bindings.md: npx burhan-kit بيشغّل النسخة المسطّبة في المشروع، وburhan لوحدها بس لو موجودة على الـ PATH. burhan عمره ما بيشغّل npm: ولو مفيش kit command بيطبع الـ setup أمر التسطيب وإنت اللي تشغّله.

  1. في جذر المشروع شغّل npx burhan-kit وبعدها npx burhan-kit doctor. الـ setup بيسأل أربع أسئلة (خمسة لو بتستخدم الـ agentين)، ويعرض summary، ومابيكتبش غير بعد ما تأكّد. setup سليم يقول all 6 hooks wired.
  2. Codex بس: وافق على الـ hooks بتاعة المشروع من /hooks، غير كده مش هتشتغل؛ ووافق عليها تاني بعد أي upgrade بيغيّر واحد.
  3. افتح session جديدة للـ agent واكتب start (أو /burhan:onboard في Claude Code). الـ agent بيقترح checks المشروع وbaseline عشان توافق عليهم.
  4. ابدأ مهمة بـ /burhan:e2e <slug> في Claude Code؛ وفي Codex اتبع الـ command file جوه .burhan/commands/. الـ process skills الستة جايين مع الـ kit؛ مفيش حاجة تانية تسطّبها.

الـ upgrade والـ uninstall والروابط

init وupgrade وuninstall مابيغيّروش حاجة لحد ما تزوّد --apply. upgrade بيجدّد ملفات الـ kit وإدخالات الـ hooks والـ skills وبيسيب الـ hooks بتاعتك؛ شغّل npx burhan-kit upgrade --apply بعد كل release. uninstall بيشيل مداخل الـ kit تحت .burhan/ (WORKFLOW.md وSETUP.md وVERSION وphases وtemplates وcommands وskills وhooks) وتحت .claude/ بيشيل بس الملفات اللي عليها علامة burhan؛ وبيسيب workflow.config وbindings.md و.burhan/local/ وملفات مهامك إلا لو زوّدت --all. أي أمر بيكتب (init وupgrade وsetup) بيرفض كتابة هتوصل لبره المشروع عن طريق symbolic link، وبيكمّل بس مع --allow-outside-links.

3. أول مهمة ليك

اطلب حاجة صغيرة، زي function ومعاها test. الـ agent بيمشي في الوقفات اللي تحت وبيستناك عند كل واحدة؛ العمود الأخير هو اللي بيشغّله. في وضع step بتشوف كل وقفة.

الوقفةإنت بتقررالـ agent بيشغّل
1 · Intakeالـ route (type وscope والسبب) مناسب ولا لأitem new <slug> --type feature --scope bounded، وبعدها guide <slug>
2 · Story وplanتجاوب على أسئلته، وتقرا الكارت، وتقول آه، وبعدها تشغّل approve story <slug> --by <name> وapprove plan <slug> --by <name> باسمك (الـ agent بيوريك الأمر)بيكتب story وplan وbuild spec، وبعدها item check <slug>
3 · Sub-unit واحدةتكمّل ولا لأ (step بيقف بعد كل واحدة)الـ test متشاف بيفشل (RED)، والكود، والـ test بينجح (GREEN)، وfast check؛ item set <slug> unit 1 in-progress، وبعدين implemented
4 · Reviewكل finding: اتصلّحت، أو discovery، أو مقبولة بسببكreviewer جديد: review add <slug> --kind review --unit 1 --by "<agent · model · context>"، finding add؛ وإنت بترد بـ finding decide؛ وبعدين item set <slug> unit 1 reviewed
5 · مفاجأةبس المشكلة اللي محتاجة قرار هي اللي بتوقّف الشغلحل معروف: deviation add <slug> … --apply "<why>" والبناء يكمّل؛ واختيار حقيقي: deviation add من غير --apply، ووقفة لحد ما تشغّل deviation resolve
6 · Verifyمين يعمل الفحص الحقيقي (الـ agent بيسأل الأول)verify <slug> -- npm test (أمرك إنت)، وبعدها review add <slug> --kind verification
7 · QCتقبل PASS، أو ترجّع المهمة للـ buildreviewer جديد: review add <slug> --kind qc --verdict PASS وfinding add <slug> --in qc --none؛ وإنت بتقبلها بـ approve qc <slug> --by <name>
8 · الإقفالأي دروس تتحفظ؛ commit دلوقتي أو بعدين أو بنفسكitem finish <slug> (بيسمّي كل gate لسه مفتوح؛ وتعلّم واحد بـ gate tick)، وبعدها state close <slug> --outcome <state> --commit <id> --folder <path>

الـ route الأصغر بتعدّي على وقفات مش محتاجاها. وفي أي لحظة guide <slug> بيقول المرحلة، وتعديل الكود مسموح ولا لأ، والخطوة الجاية.

4. الـ flow بالتفصيل

you ask → Intake → Story ✋ → Plan ✋ → Build ⇄ Review (each sub-unit)
        → Verify ✋ → QC ✋ → Knowledge ✋ → Commit ✋
✋ always you, in both modes

الـ routes

كل طلب بياخد route قبل الشغل: type (feature وbug وchange وrefactor وrelease وinvestigation، وهي للقراءة بس) وscope (bounded أو architectural؛ وpatch لتغيير واضح واحد؛ وspike للقراءة بس ولـ investigation أو تشخيص bug بس) وسبب في سطر. تقدر تصحّحه. الـ feature الـ bounded ليها موافقة واحدة على الـ story والـ plan، وبعدها build وreview وverify وQC وknowledge؛ والـ architectural ليها story وplan منفصلين، والـ plan بيعرض خيارات تصميم. أي scope escalator واحد بيخلّي المهمة architectural مهما كان حجمها: الأمان أو الخصوصية، الصلاحيات أو الرؤية، data model أو migration، الفلوس، derived state مشترك، عقود التكامل أو الـ public APIs، سلوك مايترجعش فيه، concurrency. الـ README بيسرد رحلة كل route.

الـ modes

step، وهو الافتراضي، بيقف كمان بعد build وreview كل sub-unit. auto بيكمّل بعد الـ story والـ plan، وبيحافظ على الوقفات اللي بتاعتك وبيفرمل بس لمشكلة class B (تحت). الـ commit بيقف دايمًا. قول “go end to end” لـ auto، و“wait for my approval” لـ step. الـ mode مش صلاحيات الـ agent.

الـ plan والـ sub-units

الـ plan ملفين: القرارات وbuild spec فيه test وكود كامل لكل sub-unit. الـ sub-unit بتمشي Draft → Approved → In progress → Implemented → Reviewed، درجة واحدة كل مرة بـ item set. الـ sub-unit مابتبقاش خطوة لوحدها غير لسبب مكتوب: A1 بتلمس مسار حساس أو scope escalator، A2 بتكتب قرارك أو حالة gate، A3 سلوكها محتاج test بيفشل لوحده. ستة على الأكتر؛ وitem check بيبلّغ عن سبب ناقص.

لما خطوة تغلط

الـ agent بيسأل الأول: المشكلة دي محتاجة قرار؟ Class A، من غير قرار: finding جوه المهمة وحلها بيحافظ على الـ story، أو كلام في الـ spec مش مطابق للكود، أو bug جوه الـ scope. الـ agent بيصلّحها، وبيسجّلها بـ deviation add … --apply "<why no decision is needed>" وبيكمّل؛ وguide وitem finish بيعرضوا لك كل row زي كده. Class B، قرار: تغيير في النية أو الـ scope، اختيار حقيقي، أمان، data، فلوس، أي حاجة مايترجعش فيها، تعديل test قديم، finding برّه المهمة. الـ agent بيسجّل row مفتوح بـ deviation add وبيقف؛ وguide بيقول إن الكود مش مسموح لحد ما تشغّل deviation resolve. لو في شك فهي class B. deviation done <slug> <n> --in unit:<N> بيكتب فين اتنفّذ تغيير اتوافق عليه، وitem finish بيرفض row موافَق عليه من غير الأثر ده.

الـ reviews والـ findings والـ QC

reviewer جديد بيقرا diff كل sub-unit وبيكتب تقرير فيه Performed by وبينتهي بجدول findings: finding add بيكتب row (Critical أو Important أو Minor) أو No findings.. كل row بتستنى قرارك (اتصلّحت، أو discovery، أو مقبولة بسببك، ومش مقبولة لـ Critical أبدًا)؛ وitem finish وapprove qc بيستنوا كلهم. الـ QC النهائي بيشتغل على الـ routes اللي بتطلبه، في context جديد، وبيقترح PASS أو FAIL: الـ PASS دليل، مش ضمان. QC اتكتب في نفس الـ session اللي كتبت الكود بيتحسب مراجعة ذاتية.

الإقفال

الـ knowledge review بيقترح دروس؛ وإنت بتحتفظ أو بترفض. state close بيصغّر block المهمة في ملف الحالة لسطر واحد مقفول؛ والنتيجة واحدة من QC PASS أو Done (no QC) أو Paused أو Superseded أو Already satisfied. إنت بتقفل مهمة الكود حقّق الـ story بتاعتها فعلًا بـ item close <slug> --already-satisfied "<reason>" --by <your name>.

7. كل command

كل command بيرد على --help وبيطبع بس. <slug> هو الاسم المختصر للمهمة أو رقمها أو اسم الـ folder بتاعها. أي command ماعدا init بيلاقي المشروع من أي subfolder.

الـ commandبيعمل إيه
init [dir]يسطّب الـ kit؛ dry run لحد --apply
upgrade [dir]يجدّد مشروع مسطّب؛ dry run لحد --apply
uninstall [dir]يشيل burhan؛ وبيسيب config وbindings وlocal وملفات الشغل إلا لو --all
setup [dir]setup موجّه؛ وكمان --agent و--answers <file> و--stack و--set check=… full=…
doctor [dir]فحص صحة للقراءة بس؛ exit 1 عند fail
guide [slug]المرحلة، وتعديل الكود مسموح ولا لأ، والخطوة الجاية
use <slug>يربط الـ session دي بمهمة شغّالة
item list [dir]سطر لكل مهمة: id وroute وstate
item new <slug>ينشئ ملفات المهمة وstate block بتاعها
item set <slug> …ينقل حالة plan أو sub-unit درجة واحدة
item check <slug>يسمّي كل خطأ في ملفات المهمة
item finish <slug>يكمّل الـ plan: units Reviewed وgates اتعلّمت وإثبات
item close <slug>يقفل مهمة الكود حقّق الـ story بتاعتها فعلًا

9. الذاكرة والحالة والشغل الجماعي

ذاكرة المشروع

/burhan:onboard بيخلّي الـ agent يكتب مسودة .burhan/PROJECT.md وملفات facts في .burhan/context/؛ وإنت بتوافق أو تصحّح أو تتنازل عن الـ baseline. الـ fact بيذكر مسار ملف وhash قصير، مش محتوى الملف أبدًا. memory status بيعلّم كل fact: fresh أو changed أو missing أو unchecked؛ وmemory check ممكن يشتغل في CI.

الحالة والـ sessions

ملف الحالة .burhan/local/PROGRESS.md لقطة لكل developer فيها block لكل مهمة. الـ agent بيغيّر الـ block بتاعه بس عن طريق state set وstate close، تحت lock؛ والتعديل اليدوي لسه ممكن ومفيش حاجة بتمنعه. خلّي مهمة واحدة لكل session.

الفرق والـ agents

بتتعمل لها commit وبتتراجع زي الكود: bindings.md وworkflow.config وfolders المهام (لكل واحد مالك) وPROJECT.md وcontext/. الشخصي: .burhan/local/. عمرك ما تستخدم merge=union على الملفات دي؛ بيخبّي التكرار. Claude Code بيبقى معاه /burhan:e2e و/burhan:qc و/burhan:onboard؛ وCodex بيتبع command files عن طريق AGENTS.md وبيستخدم إعدادات الـ model بتاعتك إنت، اللي burhan عمره ما بيكتبها.

10. الـ package: الـ CI والـ release

الـ CI

.github/workflows/ci.yml بيشتغل على كل push وpull request. jobs على ubuntu-24.04 وmacos-latest، الاتنين على Node 24، بتشغّل الـ lint والـ test suite كلها وnpm pack --dry-run. وjob على windows-latest، Node 24، بتشغّل الـ Node suite وbash وjq متشالين من الـ PATH. Node 22، الحد الأدنى، مابيتشغلش هناك.

الـ release

.github/workflows/release.yml بيبدأ لما tag بيطابق v* يتعمله push. guard بيفحص الـ tag على package.json والـ CHANGELOG والـ branch وnpm. verify بيشغّل lint وtests على Node 22 و24. pack بيسطّب الـ tarball المتعمل وبيشغّل burhan --version. publish بيشتغل على environment اسمه npm-release: بيستنى موافقتك بس لو ضفت نفسك مرة واحدة كـ required reviewer للـ environment ده على GitHub (من غير كده مفيش وقفة؛ وdocs/releasing.md فيه خطوات الإعداد لمرة واحدة)، وبعدين بينشر بـ --provenance، على next للـ prerelease وعلى latest غير كده. github-release بيكتب GitHub Release من الـ CHANGELOG. إنت اللي بتعمل push للـ tag، وإنت اللي بتوافق على النشر لما الـ environment يطلب كده.

الـ handbook ده مش في الـ npm package. tests/handbook.test.sh، جزء من npm test، بيفشل لو command من --help ناقص منه.

المصدر: .github/workflows/ci.yml · .github/workflows/release.yml · docs/releasing.md · docs/ci-and-windows.md · package.json

لما حاجة تبان غلط

اللي بتشوفهتعمل إيه
doctor بيفشل أو بيحذّراقرا السطر اللي بيسمّيه؛ وsetup سليم يقول all 6 hooks wired
hooks بتاعة Codex مابتعملش حاجةوافق عليها من /hooks
KIT COMMAND NOT FOUND في أول الـ sessionشغّل أمر التسطيب اللي setup أو doctor بيطبعه
guide بيقول الكود مش مسموحالـ story أو الـ plan لسه ماتوافقش عليه، أو deviation مفتوح مستني deviation resolve
item finish بيرفضبيسمّي السبب: unit مش Reviewed، أو gate مش معلّم، أو deviation مفتوح، أو واحد موافَق عليه من غير deviation done، أو finding من غير قرار، أو مفيش إثبات ناجح
verify بيطلع exit 2المهمة ماوصلتش للـ build؛ ومفيش حاجة اتسجّلت
full run: cannot tellاحفظ أمر الـ suite الكاملة: setup --set full=<regex>

الحدود

  • الـ hooks عمرها ما بتمنع؛ وأوامر المهمة بترفض خطوة غلط؛ والـ agent يقدر يتخطى الاتنين.
  • الـ hooks بتشوف بس النشاط اللي الـ agent بيبلّغ عنه؛ وتعديلات الـ shell بتظهر بس عن طريق > و>> وtee.
  • نتايج hooks بتاعة Codex محتاجة ثقة، وأمر من غير نتيجة مسجّلة مش نجاح.
  • الـ CI بيشغّل الـ Node suite على windows-latest من غير bash ولا jq: مش session حقيقية لـ agent على Windows أو macOS.
  • الـ ledger بيكبر لحد ما تمسحه.
  • الـ handbook ده لقطة: الـ stamp على الغلاف بيقول اتفحص على أنهي version.
