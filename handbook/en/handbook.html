1. What burhan is

Coding agents say “done” without proof. burhan is spec-driven development for Claude Code and Codex. The story and the plan are the spec: you approve them before any code, each acceptance criterion maps to a test, every build step is reviewed, and a step that departs from the plan is recorded. Task commands and hooks (small scripts that report at set moments) keep the record.

Keep four things apart. The agreement says what should happen. Hooks report. The ledger records what ran. You own the approvals, the commit and the risk decisions.

Terms. A sub-unit is one small planned build step. A gate is a point where the agent waits for you or for a proof (S story, P plan, T test-first build, R review, V verification, Q QC, K knowledge). QC is the final independent check that every acceptance criterion is delivered. The baseline is your approved (or waived) record of what the agent understood about the project. A knowledge review is where the agent proposes lessons worth keeping and you keep or reject them.

What it does not claim

No hook blocks an action: hooks report and fail open. Task commands refuse a wrong lifecycle step, but an agent can skip them, and the block that init writes into CLAUDE.md or AGENTS.md is an instruction, not a lock. burhan cannot prove work nobody reported.

2. Install and first setup

Requirements: Node 22+; Claude Code 2.1.139 or newer and/or Codex with its hooks trusted; the kit installed in the project (npm i -D burhan-kit) or on the PATH (npm i -g burhan-kit). Here burhan means the project's kit command, the one .burhan/bindings.md names: npx burhan-kit runs the copy installed in the project, and a plain burhan only where it is on the PATH. burhan does not run npm: with no kit command, setup prints the install command for you to run.

  1. In the project root run npx burhan-kit, then npx burhan-kit doctor. Setup asks four questions (five with both agents), shows a summary and writes only after you confirm. A healthy setup says all 6 hooks wired.
  2. Codex only: trust the project hooks in /hooks, or they do not run; trust them again after an upgrade that changes one.
  3. Open a new agent session and type start (or /burhan:onboard in Claude Code). The agent proposes the project's checks and a baseline for your approval.
  4. Start a task with /burhan:e2e <slug> in Claude Code; in Codex follow the command file under .burhan/commands/. The six process skills ship with the kit; there is nothing else to install.

Upgrade, uninstall and links

init, upgrade and uninstall change nothing until you add --apply. upgrade refreshes the kit-owned files, hook entries and skills and keeps your own hooks; run npx burhan-kit upgrade --apply after each release. uninstall removes the kit entries under .burhan/ (WORKFLOW.md, SETUP.md, VERSION, phases, templates, commands, skills, hooks) and, under .claude/, only files that carry burhan's mark; it keeps workflow.config, bindings.md, .burhan/local/ and your task files unless you add --all. Every writer (init, upgrade, setup) refuses a write that would land outside the project through a symbolic link, and goes on only with --allow-outside-links.

3. Your first task

Ask for something small, such as a function with a test. The agent walks the stops below and waits for you at each one; the right column is what it runs. In step mode you see every stop.

StopYou decideThe agent runs
1 · Intakewhether the route (type, scope, reason) fitsitem new <slug> --type feature --scope bounded, then guide <slug>
2 · Story and plananswer its questions, read the card, say yes, then run approve story <slug> --by <name> and approve plan <slug> --by <name> with your name (the agent shows you the command)writes the story, the plan and the build spec, then item check <slug>
3 · One sub-unitwhether to go on (step stops after each)the test seen failing (RED), the code, the test passing (GREEN), the fast check; item set <slug> unit 1 in-progress, then implemented
4 · Reviewevery finding: fixed, a discovery, or accepted with your reasona fresh reviewer: review add <slug> --kind review --unit 1 --by "<agent · model · context>", finding add; you answer with finding decide; then item set <slug> unit 1 reviewed
5 · A surpriseonly a problem that needs a decision stops the worka known fix: deviation add <slug> … --apply "<why>" and the build goes on; a real choice: deviation add without --apply, a stop until you run deviation resolve
6 · Verifywho runs the real check (the agent asks first)verify <slug> -- npm test (your own command), then review add <slug> --kind verification
7 · QCaccept PASS, or send the task back to builda fresh reviewer: review add <slug> --kind qc --verdict PASS and finding add <slug> --in qc --none; you accept with approve qc <slug> --by <name>

A smaller route skips stops it does not need. At any point guide <slug> says the stage, whether code edits are authorized, and the next step.

4. The flow in detail

you ask → Intake → Story ✋ → Plan ✋ → Build ⇄ Review (each sub-unit)
        → Verify ✋ → QC ✋ → Knowledge ✋ → Commit ✋
✋ always you, in both modes

Routes

Every request gets a route before work: a type (feature, bug, change, refactor, release, or investigation, which is read-only), a scope (bounded or architectural; a patch for one obvious change; a spike, read-only, only for an investigation or a bug diagnosis) and a one-line reason. You can correct it. A bounded feature has one story-and-plan approval, then build, review, verify, QC and knowledge; an architectural one has a separate story and plan, and the plan offers design options. Any one scope escalator makes a task architectural whatever its size: security or privacy, authorization or visibility, data model or migration, money, shared derived state, integration contracts or public APIs, irreversible behaviour, concurrency. The README lists every route's journey.

Modes

step, the default, also pauses after every sub-unit's build and review. auto runs on after the story and plan, keeping the stops that are yours and braking only for a class B problem (below). The commit always stops. Say “go end to end” for auto, “wait for my approval” for step. A mode is not the agent's permission mode.

The task folder

work/NNN-slug/
  NNN-slug-story.md                Draft → Approved                          approve story
  NNN-slug-implementation-plan.md  Draft → Approved → In progress → Completed   approve plan; item set; item finish
  NNN-slug-build-spec.md           exact tests, code, commands               approved with the plan
  NNN-slug-verify.jsonl            every proof run: command, exit code, time  verify
  reviews/                         review, verification and QC reports, each with a findings table
  sources/  repro/                 what you gave the agent; its scripts and logs
  NNN-slug-state-notes.md · NNN-slug-already-satisfied.md   when used

item new takes the next number. Every command accepts the number, the plain slug or the full name, and refuses one that two folders share. An old finished task with no route line and no QC file shows as Legacy in status and item list.

Plan and sub-units

The plan is two files: the decisions and a build spec with each sub-unit's complete test and code. A sub-unit moves Draft → Approved → In progress → Implemented → Reviewed, one rung at a time with item set. A sub-unit is its own step only for a written reason: A1 it touches a sensitive path or a scope escalator, A2 it writes your decision or a gate state, A3 its behaviour needs its own failing test. At most six; item check reports a missing reason.

When a step goes wrong

The agent first asks whether a problem needs a decision. Class A, no decision: a finding inside the task whose fix keeps the story, a spec wording that does not match the code, a bug inside the scope. The agent fixes it, records it with deviation add … --apply "<why no decision is needed>" and goes on; guide and item finish list every such row for you. Class B, a decision: a change of intent or scope, a real choice, security, data, money, anything irreversible, an edit of an older test, a finding outside the task. The agent records an open row with deviation add and stops; guide says code is not authorized until you run deviation resolve. When in doubt it is class B. deviation done <slug> <n> --in unit:<N> writes where an approved change was carried out, and item finish refuses an approved row with no such trace.

Reviews, findings and QC

A fresh reviewer reads each sub-unit's diff and writes a report that records Performed by and ends with a findings table: finding add writes a row (Critical, Important or Minor) or No findings.. Every row waits for your decision (fixed, a discovery, or accepted with your reason, never for a Critical); item finish and approve qc wait for all of them. Final QC runs on the routes that require it, in a fresh context, and proposes PASS or FAIL: PASS is evidence, not a guarantee. A QC written in the session that wrote the code is counted as self-review.

Closing

Knowledge review proposes lessons; you keep or reject them. state close shrinks the item's block in the state file to one closed line; the outcome is one of QC PASS, Done (no QC), Paused, Superseded or Already satisfied. You close a task whose story the code already satisfies with item close <slug> --already-satisfied "<reason>" --by <your name>.

Six process skills

burhan-storya request that changes behaviourone round of questions, the route, a story

They land in .burhan/skills/ and, for Claude Code, as copies in .claude/skills/; a skill of yours with the same name is never overwritten. A skipped skill is reported and never blocks.

Six hooks

MomentHookPurpose
Session startsession-gatesgates, task state, first-use setup, a missing kit command
Your promptprompt-routerphase and mode suggestion; baseline reminder
Before a commitpre-commit-checkthe fast check and your commit choice

Proof of “done”

The hooks run on Node, with no bash or jq, and every one fails open. When a turn edited code and claimed completion, turn-audit checks that a passing evidence command ran after the last code edit; it also flags stale state, code before a decided baseline, skipped skills, weak QC provenance and broken task-file contracts.

⚠ VERIFICATION GATE: completion was claimed, but the last run of `npm test 2>&1 | tail -15` was blocked and never ran. Run it, show the output — or retract the claim.

verify <slug> -- <command> runs a proof command itself and records its exit code in NNN-slug-verify.jsonl; item finish accepts that record, so a project without hooks still gets a recorded proof. It refuses an item that has not reached build. The ledger lives outside the project, under ~/.local/state/burhan/evidence/: reported edits, command lines and exit codes, never command output. evidence --item <slug> prints it and, like guide, ends with a full run: line: is there a passing whole-suite run after the last code edit (it needs WF_FULL_TEST_REGEX).

8. Settings

.burhan/workflow.config holds literal KEY=value lines; .burhan/local/workflow.config is git-ignored and overrides it key by key. A check whose key is empty stays silent. setup --set saves the check and the code, test, proof, whole-suite and sensitive-path settings without a hand edit.

KeyWhat it does
WF_DOCS_DIR, WF_DISCOVERY_DIRwhere the task folders and the discovery files live
WF_STATE_FILE, WF_STATE_BUDGETthe live state file and its line budget (default 80)
WF_CHECK_CMD, WF_CHECK_TIMEOUTthe fast check run before every commit, and its timeout (default 60; team-only, run upgrade after a change)
WF_STACK_SETUPpending while first-use setup is still to do
WF_CODE_REGEX, WF_TEST_REGEXwhich paths are code and tests; empty, the test-first reminder and the “done” warning stay silent
WF_EVIDENCE_REGEX, WF_FULL_TEST_REGEXwhich commands count as proof, and which one runs the whole suite
WF_SENSITIVE_REGEX, WF_SENSITIVE_NOTEpaths that affect authorization or visibility, and the reminder after editing one
WF_ITEM_CONTRACTon: the audit checks task files against the contract and warns on code edited while guide says not authorized; init writes on; absent means off
WF_MODE_DEFAULT, WF_MODE_<TYPE>_<SCOPE>step or auto; the second form sets one route
WF_MODEL_CLAUDE_REVIEWER, WF_MODEL_CLAUDE_PLANNER, WF_MODEL_CLAUDE_BUILDER, WF_MODEL_CLAUDE_EXPLORERthe model of each Claude Code role agent; empty keeps the session's model
WF_REVIEWER_AGENTwho runs QC: same, other, claude or codex
WF_EVIDENCE_LEDGER, WF_EVIDENCE_DIRon or off for the ledger, and an absolute literal path to move it

9. Memory, state and teamwork

Project memory

/burhan:onboard makes the agent draft .burhan/PROJECT.md and fact files in .burhan/context/; you approve, correct or waive the baseline. A fact cites a file path and a short hash, never file content. memory status marks each fact fresh, changed, missing or unchecked; memory check can run in CI.

State and sessions

The state file, .burhan/local/PROGRESS.md, is a per-developer snapshot with one block per item. The agent changes its own block only through state set and state close, under a lock; a hand edit is still possible and nothing stops it. Keep one task per session.

Teams and agents

Committed and reviewed like code: bindings.md, workflow.config, the task folders (one owner each), PROJECT.md and context/. Personal: .burhan/local/. Never use merge=union on these files; it hides duplicates. Claude Code gets /burhan:e2e, /burhan:qc and /burhan:onboard; Codex follows the command files through AGENTS.md and uses your own model configuration, which burhan never writes.

10. The package: CI and release

CI

.github/workflows/ci.yml runs on every push and pull request. Jobs on ubuntu-24.04 and macos-latest, both on Node 24, run the lint, the whole test suite and npm pack --dry-run. A job on windows-latest, Node 24, runs the Node suite with bash and jq removed from the PATH. Node 22, the minimum, is not run there.

Release

.github/workflows/release.yml starts when a tag matching v* is pushed. guard checks the tag against package.json, the CHANGELOG, the branch and npm. verify runs lint and tests on Node 22 and 24. pack installs the packed tarball and runs burhan --version. publish runs on the npm-release environment: it waits for your approval only if you added yourself once as a required reviewer of that environment on GitHub (without that there is no pause; docs/releasing.md lists the one-time setup), then it publishes with --provenance, to next for a prerelease and latest otherwise. github-release writes the GitHub Release from the CHANGELOG. You push the tag, and you approve the publish when the environment requires it.

This handbook is not in the npm package. tests/handbook.test.sh, part of npm test, fails when a command of --help is missing from it.

11. Problems and limits

When something looks wrong

What you seeWhat to do
doctor fails or warnsread the line it names; a healthy setup says all 6 hooks wired
Codex hooks do nothingtrust them in /hooks
KIT COMMAND NOT FOUND at session startrun the install command that setup or doctor prints
guide says code is not authorizedthe story or plan is not approved yet, or a deviation is open and waits for deviation resolve
item finish refusesit names why: a unit not Reviewed, a gate not ticked, an open deviation, an approved one with no deviation done, an undecided finding, no passing proof
verify exits 2the item has not reached build; nothing is recorded
full run: cannot tellsave the whole-suite command: setup --set full=<regex>

Limits

  • Hooks never block; task commands refuse a wrong step; an agent can skip both.
  • Hooks see only the activity the agent reports; shell edits show only through >, >> and tee.
  • Codex hook results need trust, and a command with no recorded result is not a pass.
  • CI runs the Node suite on windows-latest without bash or jq: not a real agent session on Windows or macOS.
  • The ledger grows until you delete it.
  • This handbook is a snapshot: the stamp on the cover says which version it was checked against.
